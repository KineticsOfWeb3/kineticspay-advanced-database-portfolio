
==============================================================
EXPERIMENT 3 - Query selectivity and the planner's crossover point
==============================================================
The same query shape against four accounts of very different volume. Every
index needed is already in place, so any choice of a sequential scan is the
planner deciding the index is not worth using - not the absence of one.

    account 13 :      6 postings  (0.001 % of the table)
    account 3547   :    694 postings  (0.13 %)
    account 2415  : 56,297 postings  (10.65 %)
    account 1     : 115,724 postings (21.89 %)

An index lookup costs a random I/O per matching row. Once enough of the
table matches, reading it sequentially is cheaper. That crossover is what
this experiment locates.

==============================================================
3C - LOCATING THE CROSSOVER PRECISELY
==============================================================
Experiment 3 did NOT find a sequential scan, even at 21.9% selectivity: the
planner used a Bitmap Heap Scan throughout. That is itself the finding. A
bitmap scan is the planner's middle ground - it collects matching row
locations from the index first, sorts them into physical page order, and
then reads the heap mostly sequentially. It therefore stays viable far
longer than a plain Index Scan, which would issue one random read per row.

So the real question is not "index or sequential scan" but "at what
selectivity does even a bitmap scan stop being worth it". This sweep varies
the predicate width against the same indexed column to find out.
